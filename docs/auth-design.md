# 인증 구현 설명서 — Plan-Do-See 다이어리 (과제 7)

> 비밀번호·세션 토큰·비밀키 원문은 이 문서 어디에도 적지 않았습니다. 요청·응답 근거는 `docs/evidence.md`(자동 생성, 비밀값 마스킹)에 있습니다.
> 6번 다이어리(Node.js + PostgreSQL)를 이어서 확장했고, 6번에서 입력한 내 기록은 내 계정으로 이관했습니다(T07-C100).

## ① 무엇을 붙였나
- **인증 구현 방식: 직접 구현 + 비밀번호 해시만 라이브러리** (T07-C91)
  - 가입·로그인·로그아웃·세션 발급과 폐기, 접근 제어는 6번의 Node `http` 서버 위에 직접 작성했습니다(`server.js`).
  - 비밀번호 해시는 널리 쓰이는 라이브러리 **bcryptjs 3.0.3**에 맡겼습니다. 해시 알고리즘은 직접 만들지 않았습니다 (T07-C92, C107).
  - 외부 인증 서비스(Auth0·Firebase 등)는 쓰지 않았습니다.
- API: 가입 `POST /api/signup` · 로그인 `POST /api/login` · 로그아웃 `POST /api/logout` · 내 정보 `GET /api/me` · 비밀번호 변경 `POST /api/password` · 계정 삭제 `POST /api/account/delete` · 내 자료 내보내기 `GET /api/export`
- 6번의 모든 자료(계획·수정 이력·할 일·실행 기록·완료 기록·회고)에 소유자 `user_id`를 붙이고, 모든 쿼리가 소유자 조건을 갖습니다.
- 화면: `/login`, `/signup`, 로그인 뒤 `/`(내 다이어리), `#/account`(로그아웃·비밀번호 변경·계정 삭제 안내).
- DB: `users`, `sessions` 테이블 추가, 기존 6개 자료 테이블에 `user_id` 컬럼 추가(서버 시작 시 `ALTER TABLE ... IF NOT EXISTS`로 자동 적용).

## ② 왜 그걸 골랐나
**선택 이유 (T07-C102, 인증 방식)**: 이 과제의 핵심이 "누가 어떤 자료에 접근할 수 있는가"를 코드에서 확인할 수 있게 보이는 것이라, 세션·소유자 검사 흐름은 직접 구현하고 위험한 부분(비밀번호 해시)만 검증된 라이브러리에 맡겼습니다.

**함께 검토했지만 고르지 않은 방법 (T07-C93)**
| 방법 | 안 고른 이유 |
|---|---|
| Auth0·Firebase·Supabase Auth 같은 인증 서비스 | 가입·세션이 외부에 있어 "어디를 어떻게 고쳤나"를 소스로 보이기 어렵고, 외부 계정·키 관리가 늘어남 |
| JWT(무상태 토큰) | 로그아웃·비밀번호 변경 때 이미 발급된 토큰을 즉시 무효화하기 어려움. 서버 저장 세션은 행 삭제만으로 바로 무효화됨 |
| Express + passport 등 프레임워크 | 6번이 의존성 `pg` 하나뿐인 순수 Node 서버라 구조를 크게 바꾸지 않으려 함 |

**비밀번호 해시 알고리즘 (T07-C101)**: **bcrypt** (구현은 `bcryptjs`, 비용 12). **선택 이유 (T07-C102)**: 비밀번호 전용으로 일부러 느리게 만든 알고리즘이라 유출돼도 대입이 어렵고, 솔트를 해시 안에 자동으로 넣어 계정마다 저장값이 달라지며, `bcryptjs`는 순수 JS라 Render의 Docker(alpine) 빌드에서 네이티브 컴파일이 필요 없습니다. argon2·scrypt도 후보였지만 배포 단순성 때문에 bcrypt를 골랐습니다. 비밀번호는 8자 이상 72바이트 이하(bcrypt 입력 한계).

**세션 방식 (T07-C108)**: 로그인하면 `crypto.randomBytes(32)` 토큰을 발급하고 **DB에는 SHA-256 해시만** 저장합니다. 브라우저에는 쿠키 `sid`(HttpOnly, SameSite=Strict, HTTPS면 Secure, Max-Age=3600)로만 전달하고 URL에는 절대 넣지 않습니다. 만료 시각은 `sessions.expires_at`(발급 후 1시간, 환경변수 `SESSION_TTL_SECONDS`로 변경). 서명용 비밀키가 필요 없는 구조라 코드·배포 파일·Git에 세션 비밀키가 없습니다 (T07-C113).

**거절 방식**: 남의 자료는 403이 아니라 **404**로 응답해 자료의 존재 자체를 숨깁니다 (T07-C121). 소유자 조건이 쿼리(`WHERE ... user_id = ?`)에 들어 있어서, 소유자를 확인하기 전에 쓰기가 일어나지 않습니다. 주소·헤더·본문에 적힌 사용자 정보는 서버가 무시합니다 (T07-C123).

**6번 기록 이관 (T07-C100)**: 6번에서 로그인 없이 만든 행은 `user_id`가 NULL이라 아무에게도 보이지 않습니다. 가입 뒤 `DATABASE_URL=... node scripts/claim-legacy-data.js <내 아이디>`로 내 계정에 한 트랜잭션으로 옮깁니다(구형 6번 스키마로 업그레이드 → 이관 → 다른 계정에는 안 보임을 확인함).

## ④ 안 열리는 것을 확인한 기록 (T07-C129)
`docs/evidence.md`에 요청과 응답이 나란히 있습니다 (`scripts/verify-access.js`가 자동 생성, 35개 항목 PASS).
1. 로그인 없이 `/` → 302 `/login`, 자료 API 직접 호출 → 401
2. A로 B의 자료 읽기 → 404
3. A로 B의 자료 수정·완료 처리·남의 계획 밑에 쓰기 → 404 (B 자료 변조·삽입 없음, 건수 동일)
4. A로 B의 자료 삭제 → 404
5. 로그아웃 뒤 같은 쿠키 값 재사용 → 401
(+ B→A 반대 방향, 주소·헤더·본문에 다른 계정 적기, 목록·집계·근거·내보내기 응답 검사, 만료 세션, 비밀번호 변경 후 이전 세션 무효)
검증 스크립트가 실제로 잡아내는지 소유자 조건을 일부러 빼 보는 변이 시험도 했습니다(계획/할 일/실행 기록 조회·로그아웃·만료 검사를 빼면 해당 항목이 FAIL).

## ⑥ 아직 못 막은 것 (T07-C130)
- **무차별 대입 공격(brute force)**: 로그인 시도 횟수 제한·계정 잠금이 **없음**. bcrypt가 느려 속도는 늦추지만 막지는 못함 → 약한 비밀번호는 시간을 들이면 뚫릴 수 있음.
- **비밀번호 분실 시 재설정**: 없음 → 비밀번호를 잊으면 계정을 복구할 수 없음.
- **다중 요소 인증(MFA)**, **감사 로그**(누가 언제 접근했는지 기록): 구현하지 않음.
- **아이디 존재 노출**: 가입 시 "이미 사용 중"으로 아이디 존재 여부가 드러남(로그인 쪽은 같은 문구로 숨김).
- **전용 CSRF 토큰** 없음: SameSite=Strict와 커스텀 헤더로만 완화.
- **세션 연장·기기 목록** 없음: 1시간 절대 만료, 현재 로그인한 다른 기기를 보거나 끄는 화면이 없음(비밀번호 변경 시 전부 무효화됨).
- 로그인 화면은 HTTPS가 아니면 비밀번호가 평문으로 전송됨 → 배포(Render)는 HTTPS를 쓰고, 로컬 개발만 HTTP.
